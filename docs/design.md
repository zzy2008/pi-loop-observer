# Pi Loop Observer 设计记录

更新：2026-10-04。状态：第一版核心范围已确认，尚未开始实现。下文实现细节为基于这些决策的设计方案，技术验收尚未执行。

## 编码细化

[模块详细设计](implementation/README.md) 已将下述产品决策细化为可编码的 Interface、数据契约、数据库结构、模块 Implementation 步骤与验收切片。具体实现以该文档集为准；本页保留需求与总体设计。新增方案已核对本机 Pi 1.0.0 的 turn_end 条目 ID 能力，但实际事件顺序与异常路径仍需 P0 验证。

## 已确认的产品决策

1. **目标**：学习与调试单次 agent loop。以图形实时展示执行状态和调用关系；思考与工具调用的文字记录作为节点详情。
2. **层级**：默认展示调用层，预留展开内部机制的能力。内部阶段只有具备可靠事件证据时才显示为测量结果。
3. **形态**：本地浏览器只读观察器；用户继续在 Pi 终端提问和操作。2026-10-03 核对 CLI 可行性后，用户决定暂不实施 CLI，维持此方案。
4. **图形**：每次实际 LLM 调用、工具执行生成独立节点，随运行逐步展开；并行工具分支展示，已完成轮次可折叠。
5. **联动**：实时流程图与完整时间轴联动，选择节点可查看对应调用数据。
6. **回放**：按执行阶段重现节点出现、运行、结束；详情提供完整输入输出。第一版不要求逐 token 重播。
7. **路线**：开发独立 Pi 扩展，使用官方事件采集；参考已有项目，不以 fork 现有前端作为实现基础。
8. **子 agent**：第一版作为主 agent 的工具节点展示任务、状态、耗时和结果；预留子调用关联，不展开其内部 loop。未知子 agent 工具仍按普通工具展示。
9. **问题边界**：steer 归入当前问题，在图中标记提交与生效位置；follow-up 是新问题，另建调用图并记录排队时间。划分依据 Pi 输入方式，不分析文字猜测用户意图。

## 技术栈访谈确认（2026-10-03）

前端采用 React + TypeScript + Vite，调用图采用 React Flow；首版按数十到数百调用节点验收。以模块化源码支持二次开发，暂不提供动态插件加载。

扩展启用后从 Pi 会话启动自动采集并持久化，浏览器是否打开不影响记录。`/obs` 只负责打开查看入口；Pi 不运行时，也应能独立启动服务查看历史。没有采集者和查看者并超过宽限期后服务退出，磁盘记录保留。扩展未启用时的事件不补造，中途加载和采集缺口标记不完整。这替代此前按 `/obs` 开启采集的决策。

具体技术选型、进程与数据边界、兼容性验证项见 [技术栈与运行方式](tech-stack.md)。现有设计效果图仍为模拟数据，尚未实现本节能力。

## 指定参考与会话数据复用

用户指定 [pi-provider-trace](https://github.com/Dwsy/pi-provider-trace) 作为参考。继续独立实现，借鉴其 Prompt → Turn → LLM/Tool/Message 分层、节点详情与实时/持久记录分离；源码核对及差异见 [参考实现分析](provider-trace-reference.md)。

入口命令统一为 `/obs`，职责是打开可视化查看界面，自动采集不依赖该命令。本机 Pi 1.0.0 内置命令表没有同名项；第三方扩展冲突在加载时检测。尚未实现命令注册。

数据方案建议结合 Pi 已有会话记录与 Observer 时序日志：

- Pi 会话条目提供内容、消息身份、工具参数/结果和历史分支；读取底层条目，不依赖 `/tree` 过滤后的可见行。
- Observer 官方事件采集补充开始/结束、运行中状态、并发、阶段变化与采集缺口。会话 `parentId` 与执行依赖分开建模，不能把会话树分支画成工具并发。
- 历史会话导入可在没有 Observer 采集数据时提供内容与调用关系视图。缺失的耗时/阶段标为未记录，不能凭条目相邻时间补出执行时序，也不能承诺还原 provider 层每次尝试。
- 为保持 Observer 记录可独立查看，归档所需的标准化内容与来源引用，不仅保存指向 Pi 文件的路径。原始 session 文件以后移动或删除时，已归档内容仍应可读。
- 关联使用 session/branch/entry 与 toolCall 身份；扩展回调和 session 落盘先后顺序必须实测，无法确定的映射保留未关联状态，不按文字或临近时间强行匹配。

这一数据复用方案需要技术验证后实现；目前没有导入器、关联器或真实日志。现有架构效果稿表达通用采集链路，尚未细化历史会话导入路径。

## 建议的架构（尚待实现验证）

Pi 事件适配器 → 有界事件队列 → 本地持久化与查询 → SSE → 浏览器图形界面。

事件模型、状态归约、持久化与渲染分别组织，支持未来增加采集适配器、节点详情渲染器和导出格式。辅助项目使用 pnpm，不直接修改固定基线的上游工作树。

流程图表达调用关系，时间轴表达真实起止与并发，两者消费同一份记录。实时跟随与历史查看分别管理；回放不重新执行工具。移动端采用图形与详情切换布局。

## 已发现的技术边界

- `toolcall_delta` 是模型生成参数，不是工具执行；工具执行使用 `tool_execution_*`。
- `message_update` 可观察归一化输出阶段；无需为普通状态展示修改全局 fetch。
- `after_provider_response` 只表示响应元数据到达；不能标记整个请求完成。
- `text_delta` 不保证是最终回答；无 thinking 事件不能推断模型没有内部推理。
- `agent_end` 后仍可能继续自动处理；`agent_settled` 是更可靠的运行稳定点，但不是唯一的问题划分边界。follow-up 可能在同一底层运行内被消费，不能要求每张问题图都有独立的 agent_start/end。
- SDK 的自动重试事件不等同于扩展可监听的事件集合；缺少证据的等待阶段需要明确标注，不能猜测。
- 运行中节点、正常结束、错误、取消和采集中断需要分别表达。

源码依据与候选对比见 [调研报告](research.md)。

## 页面与交互

桌面上方是问题名称、连接状态、当前活动、总耗时和实时/回放切换。主体为调用图，侧边为选中节点详情，下方为共享时间轴。

- 调用图按实际执行向前展开。例如问题 → LLM 1 → read 与 bash 并行 → LLM 2 → 回答完成。每次调用拥有独立身份；重复调用同一个工具不会覆盖旧节点。
- 节点状态使用文字、图标与颜色共同表达：排队、运行、成功、失败、取消、记录不完整。连接断开不等同于 agent 失败。
- LLM 节点展开可观察的等待、thinking、文本、工具参数生成阶段。未提供细粒度证据的内部步骤显示不可观测，不伪造持续时间。
- 同一轮可能同时存在多个活动工具。顶部显示活动集合，不能用最后一条事件覆盖其他工具的运行状态。
- 工具结果连接到消费它的下一次模型调用；时间轴按真实开始位置绘制，展示并行关系。父节点耗时与子节点耗时分别统计，避免重复相加。
- 点击任一节点或时间条，另一个视图定位同一记录；详情按需加载输入、输出、模型信息、耗时和原始事件。过大内容有明确大小与截断提示。
- 自动跟随仅在 Live 模式启用。用户缩放、拖动或查看历史时保留视口，不随新节点跳动；提供“回到实时”。
- 历史回放提供播放/暂停、前后阶段、时间游标和速度选择。游标之前的信息才参与当时状态还原；最终输出另标为“完成后详情”，避免把未来信息显示成当时已知内容。
- 已完成 turn 可折叠；图与时间轴折叠保持联动。移动端在调用图、时间轴和详情间切换，保留选中节点。

## 模块划分

| 模块 | 职责 | 边界 |
| --- | --- | --- |
| Pi adapter | 订阅官方事件，生成稳定事件信封与关联信息，管理 session/reload/shutdown | 不改变模型输入、工具执行或 agent 控制流程 |
| Trace model | 纯函数归约为问题、轮次、调用、依赖与状态 | 不依赖浏览器、Pi runtime 或数据库；实时与回放共用 |
| Recorder | 追加写入、索引、内容分离、恢复检测 | 写入失败不能阻断 agent；必须暴露采集缺口 |
| Local server | 历史查询、节点详情、SSE 增量及断线补齐 | 默认仅本机；不提供运行控制接口 |
| Web viewer | 调用图、时间轴、详情、阶段回放 | 不自行猜测 agent 状态，不重新执行记录中的工具 |

项目根目录为独立的 `pi-loop-observer/`，实现代码建议分为 `src/adapter`、`src/model`、`src/recorder`、`src/server`、`web` 和 `test/fixtures`。技术选型已收敛到 SQLite 与 React Flow，详细方案和驱动兼容性验证项见 [技术栈与运行方式](tech-stack.md)。

## 事件与数据模型

建议每条事件携带 `schemaVersion`、`eventId`、`sessionId`、`producerId`、`seq`、`traceId`、`turnId`、`spanId`、`parentId`、`wallTime`、`monotonicTime`、`type`、`payloadRef`。尚未建立归属的字段可为空；后续关联作为独立事实保存，而不是静默改写历史。

调用节点保存类型、名称、状态、起止时间、结果与输入输出引用。关联边区分包含关系、执行依赖、工具调用与工具结果；不能把单纯先后出现当作因果关系。标识包含 producer/运行范围，防止恢复或不同问题中复用 toolCallId 造成串线。

高频内容增量可合并为可见阶段与摘要，持久化完整最终内容供详情查看；保留阶段转移和生命周期边界，以支持阶段回放。耗时使用同一进程的单调时钟，跨进程仅展示可解释的时间关系。

SSE 重连按服务端持久化游标补齐并去重，不能仅凭内存快照覆盖历史。采集从运行中途开始、进程意外退出、记录缺失时标记 incomplete，而非补出不存在的开始或结束事件。

## 输入归属的实现依据与验证点

固定基线的 `InputEvent.streamingBehavior` 为 `steer | followUp | undefined`，源码位于 [types.ts](https://github.com/earendil-works/pi/blob/6160683a4a8012f0d1cd30c145df18b4ca6f5176/packages/coding-agent/src/core/extensions/types.ts)。因此能观察输入被提交时的用途。

但 `input` 发生在其他输入处理与模板展开之前，随后输入可能被变换、拦截或撤回。实际进入 agent 的 user message 没有自动携带观察器生成的 inputId。第一项技术验证应覆盖：

1. 普通输入、steer、follow-up 分别在何时提交、消费和触发下一次模型调用。
2. 多条相同文字、模板展开、输入变换、排队撤回与不同队列交错时，能否建立无歧义关联。
3. 不把 input 事件本身视为执行已开始。先登记待确认输入，实际消费后再激活 trace 或添加介入边。
4. 证据不足时明确标注未关联，不能仅凭文字相等强行匹配；若公共事件确实缺少必要 ID，应记录最小接口缺口后再决定适配方式，不直接修改固定上游基线。

现有公开接口的正常路径能区分用途，不代表以上全部边界已经可精确关联。

## 实施顺序

1. **验证事件契约**：在固定基线上用假模型与可控工具记录真实事件，验证 turn、并发、输入消费、取消和稳定点；列出能直接测量与不可观测的阶段。
2. **打通最小真实链路**：Pi 扩展 → 持久事件 → 本地服务 → 浏览器。先让两轮 LLM 与两个并发工具真实驱动图形。
3. **完善图形交互**：增量布局、状态动画、轮次折叠、时间轴与详情联动、移动端布局。
4. **加入回放与恢复**：阶段游标、重连、历史加载和不完整记录提示；验证实时结果与重放结果一致。
5. **验收与使用说明**：使用隔离配置运行集成检查，记录版本与能力边界；产出安装、启动、采集位置和扩展开发说明。

## 验收标准

- 两轮模型调用产生两个独立节点；工具调用生成和实际执行明确分开；两个并行工具具有重叠时间条。
- 单个工具失败不自动等于整次问题失败；重试、取消、等待用户与连接断开不会互相混淆。
- steer 留在当前图并标记生效处；follow-up 有独立图和排队时段。正常路径及上述输入边界均有验证证据，未覆盖情况显式标注。
- 实时与回放使用同一归约逻辑，在同一事件游标得到相同节点状态；回放不发起模型调用或工具执行。
- 浏览器刷新、断线后可恢复历史且不重复节点；进程异常退出后显示未完成记录。
- 从未打开浏览器、也未执行 `/obs` 时，已启用扩展仍记录整个执行过程；Pi 与服务退出后，通过独立查看入口可重建历史调用图与阶段回放。
- 网页中途打开时，历史加载与实时接续通过同一持久游标衔接，期间没有事件遗漏；无查看者不能导致正在采集的服务退出。
- 查看历史或详情时，新事件不抢夺视口。长记录使用折叠、虚拟化或增量布局，避免每个文本 delta 触发全图重排。
- 本地受控场景以事件产生到可见状态更新不超过 500ms 为初始验收目标；这是待测目标，不是已达到的性能承诺。长记录验收规模和设备条件随测试报告注明。
- 窄屏能完成选择节点、查看详情、切换时间位置与返回实时，整页不产生失控的横向溢出。

## 第一版范围之外
